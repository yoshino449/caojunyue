# 对话档案：线上取消预约 405，Pages Functions 方法处理器命名错误

> 日期：2026-10-09 ｜ 场景：Day3 核心功能闭环走查（线上）
> 结构：提问 → 返工 → 通过

## 提问

对线上 https://caojunyue.pages.dev 做「约 → 撞 → 取消 → 再约」闭环走查：

```
1. POST /api/bookings  {equipId:"speaker", date:"2026-10-15", slot:"第3-4节"}  → 201 ✅
2. 重复 POST 同键                                                          → 409 ✅
3. DELETE /api/bookings/4                                                  → 405 ❌
4. 再 POST 同键                                                            → 409（因 3 未删成，符合预期）
```

疑问：本地 `npm start` 走 backend/server.js 的 DELETE 全部通过（T12 五组用例），为什么线上 Cloudflare Functions 的 DELETE 返回 405？

## 返工

405 是"路径匹配但方法不被允许"。怀疑 `[id].js` 动态路由没生效，请求落到静态资产处理器（静态资产只支持 GET/HEAD）。

排查过程：

1. `git ls-files functions/` 确认 `functions/api/bookings/[id].js` 已在版本库 ✅；
2. 读 `[id].js`，发现导出的是 `onDelete`；
3. 对照 Pages Functions 官方约定：方法处理器必须命名为 `onRequestDelete`（或通用 `onRequest`），`onDelete` 不是合法导出名，Cloudflare 当作"该路径无 DELETE 处理器"处理；
4. Grep 全部 functions 导出，其余 7 处均为 `onRequestGet`/`onRequestPost`，唯独 `[id].js` 写错。

修复（一行）：

```diff
-export async function onDelete({ params, env }) {
+export async function onRequestDelete({ params, env }) {
```

commit `056977a` fix(T2): Pages Functions DELETE 处理器命名 onDelete → onRequestDelete（线上取消预约 405），push GitHub 触发重新部署。

## 通过

等部署完成后重跑闭环：

```
3. DELETE /api/bookings/4   → HTTP 204 ✅（修复生效）
4. 释放后再 POST 同键        → HTTP 201，id=5 ✅（时段已释放可重约）
5. DELETE /api/bookings/5   → HTTP 204 ✅（清理测试数据）
```

线上「约 → 撞 → 取消 → 再约」闭环全通。

## 教训

1. **平台 API 命名约定必须逐字核对**：`onDelete` 和 `onRequestDelete` 差一个前缀，框架不会报错提示，只会静默 405——这类 bug 静态检查看不出来，只能靠线上实测；
2. **验收要覆盖写操作**：此前线上验收只测了 GET 接口和页面渲染，POST/DELETE 没实测，导致这个 bug 从 T2 上线一直潜伏到 Day3 走查才暴露；
3. **闭环走查要趁早**：「约→撞→取消→再约」这种端到端用例应该上线当天就跑一遍，而不是等到验收前。

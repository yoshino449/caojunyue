# Day 5 反思

> 本轮任务：T1 测试补齐 / T2 CI / T3 互评

## 反思

1. **测试反过来推动代码可测试性**：写 T1 5 条规则测试时，才发现 server.js 直接 `server.listen(PORT)` 启动——测试无法在不启动服务的情况下 require 模块。于是抽 `if (require.main === module)` 守卫，让测试自行 `listen(0)`（随机端口）。这种"为测而改"的微重构是 TDD 的副产品，不只是验证功能，更暴露可测试性缺口。同理 `db.js` 的 `DB_FILE` 环境变量覆盖也是为隔离测试数据加的。

2. **CI 的真正价值是"能抓挂"，不是"跑绿"**：构建 #2/#3/#5/#6 全绿固然好看，但 #4 故意改错断言（409→410）触发红色失败——这才是 CI 的核心价值：人眼漏看的回归，CI 能拦住。演示时讲"5 次绿"不如讲"1 次红 + 4 次绿"，后者证明 CI 真在工作。

3. **Gitee Go schema 与 GitHub Actions 差异远大于预期**：4 条踩坑——`commands` 列表项之间不自动 `&&` 链接（GitHub Actions 用 `run: |` 多行块）、YAML 多行块报"steps 配置缺失或格式错误"、按分支发现 `.workflow/*.yml` 且默认分支是 master、社区版通知 schema 未公开（成功与失败构建均收不到站内信/邮件）。下届选 CI 平台时，Gitee Go 国内可直连是优势，但模板成熟度与文档完善度不及 GitHub Actions，需预留调通时间。

4. **AI 评审方案 ③ 的边界**：T3 互评用 AI 会话评审自己的 diff，意见真实有效（挑出了魔法数字 86400000、隐式 DB_FILE 约定、nodeVersion 易误导等真问题），整改后代码注释密度明显提升。但缺"他人视角"——AI 评审偏向代码可读性/约定，难发现"业务理解偏差"这类问题。建议下届有组员时优先真实互评，方案 ③ 仅作兜底。

# 反思录 03｜DELETE 接口用例"全线失败"——先怀疑产品，结果是测试脚本取错了 id

- 日期：2026-10-08
- 场景：T1 功能线 2（T12 后端取消预约接口）本地跑验证
- 对话结构：提问（验收）→ 返工（1 轮定位）→ 通过

## 一、提问（任务验收要求）

> 每条功能线按固定循环：任务卡 → @相关文件 → AI 实现 → 本地跑 → diff 审 → commit。
> 验收：功能在本地全流程可用。

T12 的"本地跑"设计了 5 组用例：建预约 201 → 删除 204 → 重复删 404 → 同档重约 201（验证时段释放）→ 非法 id 404。

## 二、对话还原

### 第一轮跑：用例 2~4 全红

实际输出：

```
1) 先建一条预约（期望201）: HTTP 201 {"id":11,...}
   拿到 id=1 2 5 6 7 8 11          ← 异常：id 不是单个值
2) 删除该预约（期望204）:      HTTP 404 {"error":"预约不存在"}
3) 再删一次（期望404）:        HTTP 404
4) 同器材同时段重约（期望201）: HTTP 409 {"error":"该器材在此时段已被预约..."}
5) 删除非法 id（期望404）:      HTTP 404
```

用例 4 的 409 尤其有迷惑性——像是"删除没生效、唯一索引没释放"，差点去查 db.js 的 `DELETE` 语句。

### 返工：先看证据链，定位到测试脚本本身

注意到"拿到 id=1 2 5 6 7 8 11"：这一行把**全表所有 id** 都打出来了。说明 PowerShell 管道里 `Where-Object {...} | Select-Object -First 1` 的结果在外层 `.id` 取值时发生了成员枚举，`$id` 实际是数组，拼出的 URL 变成 `/api/bookings/1 2 5 6 7 8 11`，服务端 `Number(...)` 得到 `NaN` → 404。记录 11 根本没被删，所以用例 4 重约撞唯一索引 → 409。

**产品代码没有问题，是测试脚本取 fixture 的写法错了。**

修正取 id 的写法（强制数组化再取第一个）：

```powershell
$rows = (Invoke-WebRequest -Uri "$base/api/bookings" -UseBasicParsing).Content | ConvertFrom-Json
$row = @($rows | Where-Object { $_.user -eq '取消测试-丙' })[0]
$id = [int]$row.id
```

### 第二轮跑：5 组全绿

```
定位到记录 id=11 （取消测试-丙 2026-12-12 第3-4节 10:00-11:35）
2) 删除该预约（期望204）:      HTTP 204
3) 再删一次（期望404）:        HTTP 404 {"error":"预约不存在"}
4) 同器材同时段重约（期望201）: HTTP 201 {"id":12,...}
5) 删除非法 id（期望404）:     HTTP 404 {"error":"预约不存在"}
```

## 三、通过证据

- 204 删除成功；重复删除 404；删除后同器材同日同时段可以重新预约 201（唯一索引随删除释放）；
- 随后 diff 审只含 db.js / server.js 的最小增量，提交 `e898fd6`（feat(T12)）。

## 四、反思

1. **测试脚本也是代码，同样会有 bug**：红灯先别急着改产品，顺着"造数据 → 取数据 → 发请求"的证据链找断点。
2. **异常输出就是线索**："id=1 2 5 6 7 8 11"这一行已经直接说出了病因，忽略它去查接口就会南辕北辙。
3. **fixture 要自取自带**：用业务字段（user=取消测试-丙）反查 id 并强制单值化，比手写死 id 更稳，不受重置数据库后 id 变化影响。

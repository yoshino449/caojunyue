# 对话档案：AI 助手答不出"什么时候能约"，因为上下文缺了全集参照

> 本文档基于 2026-10-14 的真实人机对话还原。

- 日期：2026-10-14
- 场景：Day10 收口——增强 LLM 预约查询助手的"可用时段"推理能力
- 对话结构：提问 → 排查返工（3 轮）→ 通过

## 一、提问（原话）

> 你：明天上午还有投影仪吗
> AI：暂无相关预约记录。
>
> 你：12月26日有投影仪吗
> AI：有。12月26日第1-2节 08:00-09:35 有 projector 预约，预约人：小米。
>
> 你：那我要预约可以预约在几号
> AI：根据现有记录，无法判断哪些日期可预约，因为数据里只列出了已有预约，没有说明各器材的库存数量或可预约上限。建议你指定想预约的器材和时段，我再帮你查该时段是否已有冲突记录。

## 二、对话还原

### 第 1 轮：先分清"模型不会"还是"它看不见"

**我**：为什么它能答出 12-26 有投影仪，却答不出哪天能约？

**AI**：这是上下文问题，不是模型问题。`buildContext` 只喂了【已有预约记录】一段——LLM 看到的是"已被占用的时段"，没有"全部器材"和"全部时段"的全集，做不了差集（空闲 = 全集 − 已占用）。

> 返工点：增强 LLM 要先看它"看得见什么"，别急着换模型或加规则。

### 第 2 轮：补全集参照 + 同时立推理规则

**AI**：`buildContext` 改成三段式——【全部器材】（projector / camera / speaker）+【全部时段】（5 个时段及时间）+【已有预约记录】。LLM 有了全集，就能算出"第3-4节到晚间没被 projector 约过 → 这些时段可用"。

**我**：那它会不会还是保守地说"无法判断"？

**AI**：所以同时改 `SYSTEM_PROMPT`：新增"没出现在预约列表 = 可用""先算出'明天'是哪天，再找该日该器材的预约""不要说'无法判断'——数据是全量的"。8 条规则里 3 条专治这个。

> 返工点：给 LLM 补数据和给 LLM 立规则要一起做，只补数据它仍可能"安全地回答不知道"。

### 第 3 轮：为什么不在服务端硬算

**我**：能不能后端直接把可用时段算好再给 AI？

**AI**：可以但更脆。服务端硬算要先解析"明天"是哪天、把"投影仪"映射成 `projector`——正则提取易漏；LLM 天然理自然语言，给它全集 + 规则让它做集合推理更稳。改动也小：只动 prompt 与 `buildContext`，不碰接口契约。

> 返工点：能用 LLM 的语义理解解决的，别用服务端正则硬扛。

## 三、通过证据

- commit `b65985d`（feat: AI 助手补全集参照 + 推理规则）；
- 本地 5 条业务规则测试全绿（`node --test tests/api.test.js`，5 pass / 0 fail）；
- 上下文由"仅已有预约"扩为"全部器材 + 全部时段 + 已有预约"三段。

## 四、反思

1. **LLM 答不对，先查上下文再怪模型**：同一个 DeepSeek，喂全信息就能推理，缺全集就只会念记录；
2. **补数据与立规则要同步**：光补全集，LLM 仍可能保守回避；要显式禁止"无法判断"并给出推理路径；
3. **语义问题别用正则硬解**：日期、器材别名的解析交给 LLM 更稳，服务端只负责把事实喂全。

## 一、提问（原话）

> T1 交叉验收：clone 组员仓库，跑全接口测试轨 + PRD 12 功能 AC 走查。

## 二、对话还原

### 第 1 轮：不能只看代码，要跑起来

**我**：帮我看看组员仓库写得怎么样。

**AI**：先 clone → 启动后端 8080 → curl 实测，而不是读代码猜接口。全接口测试轨（13 个接口）+ PRD 12 功能 AC 走查，共发现 13 条缺陷（必须修 10 + 建议修 3）。

> 返工点：只看代码容易误判（以为某接口存在）；13 条缺陷全部来自真实 500/400/200 证据，没有一条是猜的。

### 第 2 轮：issue 提交撞每日上限 + CAPTCHA

**我**：把缺陷整理成 issue 提交。

**AI**：拆成 11 条 issue，提交到**第 5 条触发 Gitee 账号每日发布上限**，剩余 6 条只能次日继续。用浏览器代理填表单时，字符点击验证的 CAPTCHA 容器渲染尺寸为 `0x0`，无法自动完成。

> 返工点：大批量提 issue 前要预估数量、分多天提交；「提交」这一步必须真人操作。

### 第 3 轮：修 Issue 1/2，带证据再发

**我**：先把能修的修掉。

**AI**：修复 Issue 1（业务规则 3：日期 7 天上限）+ Issue 2（业务规则 2：每人每天 3 次上限），改动 `BookingRepository.java` + `BookingService.java`，`mvn compile` 通过、`mvn test` 5 用例全绿。

> 返工点：不能只说「应该好了」，要 compile + test + 复现脚本输出，把证据贴进 PR 描述。

## 四、反思

1. **交叉验收要「跑起来」再下结论**：clone → 启动 → curl 实测是唯一可信依据；
2. **修复要带验证证据再发 PR**：compile、test、复现输出缺一不可；
3. **Gitee 每日发布上限要提前规划**：大批量 issue 分多天提交，或用 API（同样受上限约束）；
4. **CAPTCHA 在自动化环境不可靠**：填表能省时间，但「提交」必须真人操作。

## 反思

### 1. 缺陷清零的范围界定：只修影响演示的

Day 9 要求"只修影响演示的 bug"，但实际执行时容易扩大范围。本次自查发现两类残留：一是 `functions/api/bot/` 调试路由（Day7 排查 ai 命名问题时的测试产物，commit 204e76f 留下）；二是 `.gitignore` 未覆盖 `.trae/` 和 `debug.log`。两者都不影响演示闭环，但会让评委 clone 仓库时看到脏工作树。结论：缺陷清零的"影响演示"判定应包含"仓库第一印象"——评委不只看线上，也会 clone 代码。

### 2. 演示数据的盲区：前端 date>=today 过滤

线上 D1 有 2 条 seed 预约，但日期都是过去的（10-09 / 10-10）。前端 `b.date >= todayStr()` 过滤后，三张卡片全部显示"近期预约（0）"——评委第一眼就是"暂无数据"。教训：演示数据准备不能只看 API 返回非空，必须走前端渲染确认；前端过滤逻辑会让"API 有数据"和"页面有数据"脱节。POST 3 条今天/未来预约后，每个器材各显示 1 条，评委视角正常。

### 3. PPT 草稿选型：自写 HTML vs html-deck skill

本次路演 PPT 用纯手写 HTML（6 页 + 方向键翻页），未用 html-deck skill。权衡：skill 产出动画丰富但耗时且风格不可控；手写 HTML 6 页约 200 行，30 分钟完成，内容完全自主，且可作为"页面草稿"双用途（既能投影也能浏览器打开）。结论：3 分钟路演的 PPT，内容密度比视觉炫技重要；skill 适合正式答辩，草稿阶段手写更快。

### 4. 彩排刺的分级：砍 vs 救

Day 9 T2 要求"当场决定砍/救哪些功能——今天砍掉的功能比救活的更常见"。本组彩排刺集中在三处：（1）AI 助手线上 Key 额度用尽时兜底提示是否够清晰；（2）统计图表 CDN 被墙时的 fallback 提示；（3）取消操作不校验预约归属（PRD 已记录限制）。决策：保留（1）兜底已实现、（2）已 fallback、（3）属 PRD 明确不做的 P2。结论：砍功能比救功能更需要勇气，但 PRD 的"明确不做清单"是最高挡箭牌。

## 待改进

1. **演示数据应进 seed.sql 而非临时 POST**：当前演示数据是临时 POST 到 D1 的，Cloudflare 重新部署不会丢（D1 持久化），但如果换库或重置 D1 会消失。建议把演示数据日期改为"相对今天"的动态计算写入 seed.sql，或单独维护 `db/demo-seed.sql`，让演示数据可复现。
2. **PPT 应补"失败兜底"演示分支**：当前 PPT 第6页只走 happy path（约→撞→取消→再约），未演示 AI 助手失败兜底（503/504/429）。评委可能问"AI 挂了怎么办"，应在 PPT 或演示脚本中补一条"断网→兜底提示"分支，证明失败场景也有合理提示。

# 反思录 02｜Pull Request 合并被"审核门禁"拦截——改设置后重发才通过

- 日期：2026-10-07
- 场景：Gitee Pull Request 练习
- 验收要求：Gitee 仓库 main 分支提交历史里能看到本 PR 的合并记录
- 对话结构：提问 → 返工（2 个坎）→ 通过

## 一、提问（原话）

> 先 clone 自己的仓库跑通推拉；然后再进自己的仓库：fork → 改一行 README 欢迎语 → 发 Pull Request → 合并 → 你网页上能看到改动。
> 验收：Gitee 仓库 main 分支的提交历史里能看到你这条 PR 的合并记录。

## 二、对话还原

### 坎 1：Gitee 不能 fork 自己的仓库

**AI**：核实平台行为后说明：Gitee 不允许 fork 自己的仓库。课程这个环节的等价做法是「特性分支 + 同仓库 Pull Request」，最终 main 历史一样留下 "Merge pull request" 记录，验收效果一致。

随后：新建 `main` 并推送到远程 → 网页把默认分支从 master 切到 main（中途踩到 Semantic UI 自定义下拉：直接 `.value=` 和回车都不生效，最后用"搜索框过滤 main → click 菜单项"才选中）→ 从 master 切出 `feat/readme-welcome`，加欢迎语 "👋 欢迎来到本项目，一起加油！——第9组 曹骏越"，提交 `b0fa8cd` 推送 → 发起 PR **!1**（第一次还把源/目标方向填反，页面提示"两个分支没什么不同"，交换参数顺序后才进入正常表单）。

### 坎 2：!1 被审核门禁拦截，"自审"不算数

**现象**：PR !1 页面显示"此 Pull Request 暂不能合并，一些审核尚未通过"。

**第一次尝试（无效）**：页面上点了「审查通过」「测试通过」，两行都显示"已完成 (1/1人)"，但合并区仍然提示不能合并。

**定位**：仓库「管理 → 代码审查设置」里默认配置了"至少需要 1 名审查人员 / 1 名测试人员通过后可合并"，而这类平台的通用规则是 **PR 作者自己的审批不计入有效审核**——一个人不能做自己代码的审查者。

**返工动作**：

1. 把两项人数要求从 1 改为 0，保存（页面说明：该设置"不会影响已创建指派的 Pull Request"）；
2. 所以 **!1 即使设置改了也不会被追溯放行**——关闭 !1；
3. 用新规则重新发起 PR **!2**；
4. 这次合并区显示"源分支与目标分支没有冲突，可自动合并"；
5. 点「合并分支」→ 弹层确认「接受 Pull Request」。

> 关键认知：门禁是**仓库设置**，不是 bug 或页面卡死；改设置属于协作规则变更，且对存量 PR 不追溯——必须重发。

## 三、通过证据

- PR !2：https://gitee.com/cao-junyue/caojunyue/pulls/2 ，状态"已合并"；
- main 提交历史：https://gitee.com/cao-junyue/caojunyue/commits/commits/main 顶部即
  `937e353 !2 docs: README 增加欢迎语 — Merge pull request !2 from 曹骏越/feat/readme-welcome`；
- 本地 git 交叉验证：`937e353 parents: 5eaf413 b0fa8cd`（真合并提交，双父节点），main 上 README 含欢迎语；
- PR !1 留在"已关闭"列表，作为完整痕迹保留。

## 四、反思

1. **平台约束要绕得诚实**：不能 fork 自己就换等价的特性分支流程，并主动说明差异，而不是伪造一个 fork 截图交差。
2. **自审无效是刻意设计**：代码审查的意义在于"第二双眼睛"，工具用流程强制这一点；个人练习仓库可以降到 0 人，但团队仓库不该关。
3. **设置变更要看生效范围**："不影响已创建的 PR"这句话决定了必须"关闭 → 重发"，而不是反复刷新 !1 等它放行。

# PRD：教务器材预约（Equipment Booking）

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-10-07 |
| 作者 | （组内填写） |
| 状态 | 待审改 |
| 上游文档 | T3 电梯稿（组内互讲版） |

> **一句话定位**：一个零依赖网页，老师选器材、选日期与时段完成预约；同一器材同一时段自动互斥，杜绝"群里口头约、撞车才知道"。

## 1. 背景与问题

公共器材（投影仪、单反相机、便携音响）的借用现状：

- 靠微信群口头约定 + 纸质登记，约没约上全凭记性；
- 占用信息散落在聊天记录里，教务员无法一眼看清；
- 口头约定不可追溯，撞车后责任说不清。

## 2. 目标用户与场景

| 用户 | 典型场景 | 使用频率 |
|---|---|---|
| 任课老师 | 明天第 3-4 节要用投影仪，打开页面看占用、点「预约」 | 每周数次 |
| 教务员 / 设备管理员 | 集中查看三台器材被谁占用，或代老师登记 | 每天 |

## 3. 用户故事

1. 作为老师，我想看到每台器材近期的预约列表，以便挑空闲时段。
2. 作为老师，我想按日期和时段提交预约；时段被占用时要**当场被拒绝并知道原因**，而不是事后撞车。
3. 作为老师，我约错了想取消；取消后该时段要能被别人重新约到。
4. 作为教务员，我想在一屏内看全三台器材的占用情况。

## 4. 功能需求

### P0（v1 必须，砍掉则产品不成立）

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 浏览器材 | 三张卡片：📽️ 投影仪 Epson CB-FH06 / 📷 单反相机 Canon EOS 850D / 🔊 便携音响 JBL EON ONE COMPACT；每张展示**今天起**的预约（日期 + 时段 + 预约人），按日期升序 |
| F2 | 提交预约 | 点「预约」弹窗填写：预约人 + 日期 + 时段（五选一：第1-2节 08:00-09:35 / 第3-4节 10:00-11:35 / 第5-6节 14:00-15:35 / 第7-8节 16:00-17:35 / 晚间 19:00-21:00）；成功后记录立即出现在卡片 |
| F3 | 时段互斥 | 同一「器材 + 日期 + 时段」仅允许一条有效预约；重复提交在弹窗内红字提示「该器材在此时段已被预约，请更换日期或时段」，**不写入数据** |

### P1（v1.1，可砍项）

| 编号 | 功能 | 说明 |
|---|---|---|
| F4 | 取消预约 | 每条记录旁「取消」按钮 + 二次确认；确定后记录删除、时段立即释放可被重新预约。⚠️ v1 无账号体系，不做"仅本人可取消"的归属校验（单登记人场景可接受） |
| F5 | 输入校验 | 预约人 / 日期 / 时段必填；不可提交过去的日期 |
| F6 | 预约统计 | 页面提供「统计」入口，用图表展示各器材预约量（柱状）与各时段热度（饼图）；数据来自服务端聚合（`GET /api/stats`），随预约/取消实时变化。依赖 Chart.js（CDN 引入，零构建） |

### P2（远期，见 §8 不做清单）

后端判重、登录、审批流、通知。

## 5. 非功能需求

- **零依赖**：单个 index.html，双击即可打开；无网络、无构建。
- **持久化**：预约存 localStorage，刷新 / 重开浏览器不丢。
- **效率**：一次预约操作 ≤ 15 秒完成。
- **样式**：简洁（浅灰底、白卡片、蓝色主按钮），不需要设计资源。
- **兼容**：Chrome / Edge 最新版。
- **线上可访问**（T2）：部署到 Sealos DevBox（国内容器平台 cloud.sealos.io，国内可直连；render.com/zeabur.com 国内打不开故弃用）。Sealos「应用管理 → 新建应用」只接受镜像名不接受源码，源码部署走另一个入口「DevBox」（云端开发 + 一键发布为正式应用，不用本地装 Docker），提供 `*.sealos.io` 子域名，教师手机可直接打开看到真实预约数据。
- **访问统计**（T2）：页面页脚展示访问计数（自建 `visits` 表，`GET /` 时自增），满足"访问统计"要求。
- **部署持久性限制**：容器文件系统不持久（重启清库），服务启动靠 `ensureDb()` 自动建表+seed 自愈；访问计数在重启后归零——已知限制，如实记录于 `docs/部署手册.md`。

## 6. 验收标准（AC）

| # | 验收项 | 通过标准 |
|---|---|---|
| AC1 | 卡片展示 | 3 张卡片可见，含图标 / 名称 / 型号 / 近期预约列表 |
| AC2 | 预约成功 | 完整填写提交后出现「预约成功」提示，卡片新增记录 |
| AC3 | 重复拒绝 | 同器材同日期同时段第二次提交：弹窗红字提示、弹窗不关闭、数据不变 |
| AC4 | 互斥范围 | 互斥仅限「同器材 + 同日期 + 同时段」；换时段、换器材均可成功 |
| AC5 | 取消释放 | 取消确认后记录消失，同时段立即可被他人预约成功 |
| AC6 | 持久化 | 刷新页面后记录仍在 |
| AC7 | 过去日期 | 过去日期被拦截 |
| AC8 | 预约统计 | 点「统计」出图：柱状图展示三台器材预约量、饼图展示各时段热度；新增/取消预约后重开统计，数字随之变化 |

## 7. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| localStorage 仅本机生效：两位老师在不同电脑约同一时段**不会互斥**，真实场景会撞车 | 高 | v1 明确锁定「单登记人（教务员）代登记」场景并在页面注明；v2 把判重上移最小后端，前端数据结构不变 |
| 原生 confirm 在个别环境被拦截 | 低 | 观察项；必要时改为页内二次确认 |

## 8. 明确不做（Out of Scope，v1）

❌ 后端服务与跨设备互斥　❌ 登录 / 账号体系　❌ 借用审批流与通知　❌ 编辑预约（只能取消后重约）　❌ 历史预约展示（仅今天及以后）

## 9. 可行性与已有基础（凭什么做得完）

- 对应已学课程：HTML/CSS 页面与布局、JS DOM 与事件、localStorage 数据持久化；
- 已有可点击原型验证过「约 → 撞 → 取消 → 再约」完整闭环，无技术未知数。

## 10. 审题三问

1. **用户真实存在？** 存在——借器材上课的老师与登记的教务员是现存高频流程。
2. **砍掉 1 个功能行不行？** 行，先砍 F4 取消：「浏览 + 预约 + 互斥」已是完整闭环。
3. **演示第一眼看什么？** 三张卡片 → 现场制造冲突（同时段连约两次被当场拦下）→ 一句话点题「自动互斥」。

## 1. 总体架构

```
index.html（单文件，零依赖、零构建、无网络请求）
├── <style>   样式：浅灰底 / 白卡片 / 蓝主按钮 / 弹窗遮罩 / toast
├── <body>    结构：header + #cards 卡片区 + 预约弹窗 overlay（独立于卡片区）+ toast
└── <script>  逻辑：存储层 / 渲染层 / 弹窗层 / 业务层

数据：localStorage['equipment_bookings_v1']（JSON 数组）
```

双击 index.html 即可运行（file:// 下 localStorage 同样可用）。

## 2. 数据模型

```js
// localStorage['equipment_bookings_v1']
[
  {
    equipId: 'projector' | 'camera' | 'speaker',
    user: '张三',                 // 预约人姓名
    date: 'YYYY-MM-DD',          // 本地日期
    slot: '第1-2节 08:00-09:35', // 五个固定时段之一
    createdAt: 1791337350000
  }
]
```

**互斥唯一键：`equipId + date + slot`**（对应 PRD F3 / AC4）

## 3. 模块职责

| 模块 | 函数 | 职责 | 关键约束 |
|---|---|---|---|
| 存储 | loadBookings / saveBookings | 读写 localStorage | JSON 解析失败返回 `[]` |
| 渲染 | renderCards | 全量重绘三张卡片与预约列表 | 仅展示 date ≥ 今天、按日期升序；用户输入 escapeHtml 后再入 DOM |
| 弹窗 | openModal / closeModal / showError / showToast | 表单显隐与提示 | 弹窗 DOM 独立于 `#cards` 之外，重绘不触碰弹窗显隐（防"数据刷新连带重建 UI"的状态污染） |
| 业务 | submitBooking / cancelBooking | 校验、判重、写入 | 唯一键判重；取消用原生 confirm 二次确认 |

## 4. 关键流程

### 4.1 预约（含判重）

```
点卡片「预约」→ openModal(equipId)（记录 currentEquipId，date.min = 今天）
→ 填表 → 点「提交预约」→ submitBooking()
   ├─ 校验：必填 + date ≥ 今天，失败 → showError
   ├─ 判重：list.some(b => b.equipId===currentEquipId && b.date===date && b.slot===slot)
   │    命中 → showError('该器材在此时段已被预约…')，return（不写数据）
   └─ 通过 → push + saveBookings + closeModal + renderCards + toast('预约成功')
```

### 4.2 取消（时段释放）

```
点记录「取消」→ confirm('确定取消 … 吗？')
   ├─ 放弃 → return（数据不变）
   └─ 确定 → 按唯一键过滤 → saveBookings + renderCards + toast('已取消预约')
```

## 5. 选型理由与代价

| 决策 | 理由 | 代价 / 对策 |
|---|---|---|
| 单文件原生 JS，不用框架 | 功能规模小，引入框架 + 构建链性价比为负；课程所学即原生三件套 | 逻辑集中在一个文件，靠注释分区维护 |
| localStorage 存数据 | 零部署、刷新不丢 | 跨设备不互斥 → v2 判重上移服务端（PRD 已声明） |
| renderCards 全量重绘 | 状态单一、实现简单 | 数据量大时有损耗，当前量级可忽略 |

## 6. 安全

- 用户输入（预约人姓名）经 escapeHtml 转义后插入 innerHTML，防 XSS；
- localStorage 仅存姓名 / 日期 / 时段，无敏感信息。

## 7. v2 升级路径

- submitBooking 里前端 `some()` 判重 → 改为 `POST /api/bookings`，服务端按唯一键再次校验（防并发竞态）；
- 最小后端：Node 原生 http + JSON 文件即可，无需数据库；前端数据结构不变。

## 8. 测试策略

- 按 PRD AC1–AC8 人工走查，真实浏览器 UI 操作（含 confirm 两个分支）；
- 回归重点：判重命中 / 不命中、取消后同时段可再约、刷新持久化、控制台无报错；
- T1 统计专项：连续开关统计弹窗不报 canvas 复用错（验证 destroy）；新增/取消预约后重开统计数字变化。

## 9. 预约统计（T1：Chart.js 接入）

### 9.1 端点设计

`GET /api/stats` → `200`
```json
{
  "perEquip": [{ "equipId": "projector", "count": 3 }, ...],
  "perSlot":   [{ "slot": "第1-2节 08:00-09:35", "count": 2 }, ...]
}
```
两条 `GROUP BY` 聚合查询在 `db.js#getStats()`，**聚合走服务端、前端不做计算**（避免把全量预约数据拉到前端再 for 循环，也便于后续扩展按日期范围筛选）。

### 9.2 前端接入

- head 引入 `<script src="https://cdn.jsdelivr.net/npm/chart.js@4" defer>`（CDN，零构建、零 npm 依赖）；
- header 加「统计」按钮；新增独立统计弹窗（复用 `.overlay` 遮罩样式，DOM 与预约弹窗平级、互不影响），内含两个 `<canvas>`，外层容器固定高度 260px；
- `loadStats()`：fetch `/api/stats` → `new Chart(ctx, {...})`；`type:'bar'`（各器材预约量）+ `type:'doughnut'`（各时段热度）。

### 9.3 坑点清单（已踩过，README 同步记录）

1. **canvas 复用报错**：同一 canvas 再次 `new Chart()` 会抛 "Canvas is already in use"。对策：模块级缓存 chart 实例，再次打开前先 `.destroy()` 旧实例。
2. **响应式拉伸**：默认 `maintainAspectRatio:true` 会导致图表随容器宽度无限拉高。对策：`options:{maintainAspectRatio:false, responsive:true}` + 父容器固定高度。
3. **CDN 可用性**：jsdelivr 在个别网络环境被墙。对策：页面加加载态，Chart 全局对象未定义时按钮禁用并提示"统计组件加载失败，请检查网络"；不阻塞主预约流程。
4. **聚合时机**：统计弹窗每次打开都重新 fetch `/api/stats`（不缓存），保证数据随预约/取消实时变化。

## 10. 部署架构（T2：Render 备选，Sealos DevBox 已弃）

> 历史：原计划 Sealos DevBox（cloud.sealos.io，国内容器平台），但 cloud.sealos.io 改版后实际页面与教程差距大、登录与创建项目环节卡住过不去；后改用 Render（render.com，国内可直连、Free $0/月），但 Render Free 计划**首次创建 Web Service 必须绑 Visa/Mastercard 国际卡做身份验证**，无国际卡无法通过；当前主流程已切换到 Cloudflare Pages（详见 §11），Render 降为备选保留给有国际卡的同学。Render Node runtime 默认 24，满足 `node:sqlite` 所需 ≥22；仓库根 `render.yaml` 已就位（type=web/runtime=node/branch=main/plan=free/startCommand=`node --experimental-sqlite backend/server.js`/healthCheckPath=/ping/autoDeploy=true），代码一行不改。

### 10.1 关键改动（与平台无关，Render/Sealos 通用）

| 改动点 | 位置 | 原因 |
|---|---|---|
| 端口走环境变量 | server.js：`const PORT = process.env.PORT || 3000` | 平台通过 `PORT` 环境变量注入端口，硬编码 3000 会绑定失败 |
| 启动自愈建库 | server.js 已有 `ensureDb()` 调用 | 免费档文件系统不持久（重启清库）；启动幂等建表+seed，自动恢复可演示状态 |
| 访问计数表 | db/schema.sql 新增 `visits` 表（单行计数器） | 满足"访问统计"要求，自建、零依赖、不引第三方分析服务 |
| 计数自增时机 | server.js：`GET /` 返回 index.html 前调 `incrementVisits()` | 每次「打开页面」计一次，不计 API 与静态资源请求 |
| 计数查询端点 | server.js：`GET /api/visits` 返回 `{count}` | 前端页脚启动时拉取展示 |
| Node 版本约束 | package.json：`engines.node >= 22` | 平台据此选 Node 22（`node:sqlite` 实验性所需） |

### 10.2 ephemeral 持久性限制（如实记录）

- 免费档：有用量上限/休眠策略，重启清空 `data/` 目录；
- 后果：访问计数在重启后归零、预约数据回到 seed 示例（2 条）；
- 这是免费档已知限制，不修（持久化需付费卷或换数据库，超出 T2 范围），手册如实写明。

### 10.3 部署配置

- **Render（主，国内实测可直连）**：仓库根 `render.yaml` 声明式 Blueprint（type=web/runtime=node/branch=main/plan=free/startCommand=`node --experimental-sqlite backend/server.js`/healthCheckPath=/ping/autoDeploy=true）；dashboard.render.com 注册（用 GitHub/Google/邮箱，无需实名）→ New → Web Service → 连接 GitHub 仓库 → 填字段（Name/Region=Singapore/Build=留空/Start Command=node --experimental-sqlite backend/server.js）→ 选 Free 计划 → Advanced 设 Health Check Path=/ping → Create Web Service → 拿 `*.onrender.com` 域名；**不需要本地装 Docker、不需要 Dockerfile**；详见 `docs/部署手册.md`。
- **Render Docker runtime（备选，绕过 Node 版本不确定性）**：仓库根 `Dockerfile`（`node:22-slim` + `--experimental-sqlite` + EXPOSE 3000），在 Render 创建 Web Service 时 Runtime 选 Docker 而非 Node；详见手册附录 B。
- **Sealos DevBox（备选，cloud.sealos.io 改版后流程不匹配）**：仓库根 `entrypoint.sh` 作为 DevBox 发布为正式应用时的 OCI 镜像入口点；旧版流程详见手册附录 C（仅供记录，**不再推荐**）。

## 11. 部署架构（T2 主线：Cloudflare Pages + Functions + D1）

> 选型：Render Free 要绑国际卡（用户没有），Sealos DevBox 改版后流程不匹配。实测 Cloudflare Pages 满足：注册**不要绑卡、不要手机号**、可用 GitHub OAuth、国内可直连（有中文验证码）、Free $0/月、域名 `*.pages.dev`。但 Cloudflare 路线要改架构：后端从 Node http + node:sqlite 换成 Pages Functions（ESM）+ D1 binding，违反 AGENTS.md「CommonJS / node:sqlite / 禁第三方驱动」三条约束。按改动纪律，**保留 backend/ 不动作为本地开发路径**，新增 `functions/` 子树作为 Cloudflare 适配层，**二者并列、互不替换**。

### 11.1 双轨架构（本地 Node + 线上 Cloudflare）

```
本地开发（npm start）            线上部署（Cloudflare Pages）
─────────────────────────       ──────────────────────────────
backend/server.js               functions/index.js
  ├ http.createServer           ├ onRequestGet（GET /：自增 visits）
  ├ /ping                       ├ functions/ping.js
  ├ /api/bookings GET/POST      ├ functions/api/ping.js
  ├ /api/bookings/:id DELETE    ├ functions/api/bookings/{index,[id]}.js
  ├ /api/stats                  ├ functions/api/stats.js
  ├ /api/visits                 ├ functions/api/visits.js
  └ 静态托管 frontend/          └ env.ASSETS.fetch（Pages 内置静态资源）
       │                              │
       ▼                              ▼
backend/db.js                   functions/_lib/queries.js
  node:sqlite（同步）            D1 binding env.DB（异步）
       │                              │
       ▼                              ▼
data/equipment.db（本地文件）    D1 数据库（远程 SQLite，持久）
```

### 11.2 路由映射（5 路由 + visits 自增）

| 原后端路由 | Pages Function 文件 | 备注 |
|---|---|---|
| `GET /ping` | `functions/ping.js` | 返回 `ok` |
| `GET /api/ping` | `functions/api/ping.js` | 同上 |
| `GET /api/bookings` | `functions/api/bookings/index.js#onRequestGet` | listBookings(env) |
| `POST /api/bookings` | `functions/api/bookings/index.js#onRequestPost` | 校验 + createBooking，唯一冲突→409 |
| `DELETE /api/bookings/:id` | `functions/api/bookings/[id].js#onDelete` | 204/404 |
| `GET /api/stats` | `functions/api/stats.js` | 两条 GROUP BY |
| `GET /api/visits` | `functions/api/visits.js` | 返回 `{count}` |
| `GET /`（自增 visits + 托管） | `functions/index.js#onRequestGet` | 见 §11.3 |

映射规则遵循 Pages Functions 文件路由约定（`[id]` = 路径参数；`index.js` = 目录本身）。前端 fetch 路径**完全不变**。

### 11.3 访问计数实现

`functions/index.js#onRequestGet`：

1. `await env.DB.prepare('UPDATE visits SET count = count + 1 WHERE id = 1').run()`
2. `return env.ASSETS.fetch(new Request(new URL('/', request.url)))`

`env.ASSETS` 是 Pages 自动注入的静态资源 binding，仅线上 / `wrangler pages dev` 存在；本地仍走 `npm start`（Node + node:sqlite），双轨并行。**不用 `_middleware.js`**（会拦所有路径，多余；GET / 路径自增语义在 functions/index.js 已实现）。

### 11.4 数据访问层（functions/_lib/queries.js）

抽共享模块，导出 `listBookings / createBooking / deleteBooking / getStats / incrementVisits / getVisits`，**签名与 backend/db.js 完全对齐**，差别仅在内部：用 `env.DB.prepare(...).bind(...).all()/get()/run()` 替代 `openDb().prepare(...).run()`。SQL 字符串集中放此文件，各 Function 只 import 调用，不散 SQL。

适配点：
- D1 的 `meta.last_row_id` 替代 node:sqlite 的 `lastInsertRowid`；
- D1 `prepare().all()` 返回 `{results, meta}`，需取 `.results`；
- 唯一约束冲突用相同正则启发式（`SQLITE_CONSTRAINT_UNIQUE` / `UNIQUE constraint`）→ 抛 `BookingConflictError` → Function 返回 409，前端契约不变。

### 11.5 wrangler.toml 配置

```toml
name = "caojunyue"
compatibility_date = "2026-10-08"
pages_build_output_dir = "frontend"

[[d1_databases]]
binding = "DB"
database_name = "equipment-booking"
database_id = "<部署后回填>"
```

Functions 自动从仓库根的 `functions/` 读取，无需在 toml 声明。

### 11.6 约束冲突说明（AGENTS.md 同步更新）

`functions/` 子树用 ESM 是 Cloudflare Pages Functions 运行时硬性要求，与 AGENTS.md「CommonJS（require / module.exports）」条款冲突。对策：**仅 `functions/` 子树用 ESM**，`backend/` 仍 CommonJS；二者互不混用，本地 `npm start` 不依赖 `functions/`，线上 Pages Functions 不依赖 `backend/`。D1 binding 是 Cloudflare 平台注入的运行时对象（`env.DB`），不是 npm 包，不算「引入第三方 ORM / 数据库驱动」。

### 11.7 部署流程（详见 docs/部署手册.md 主流程章）

1. 注册 Cloudflare（GitHub OAuth，不绑卡）
2. **先建 D1**：Storage & databases → D1 → Create database → 名 `equipment-booking` → Console 粘贴 `db/schema.sql` + `db/seed.sql` 执行
3. **再建 Pages**：Workers & Pages → Create application → Connect GitHub → 选仓库 + main → Build command 留空 → Build output directory = `frontend` → Save and Deploy
4. **配 binding**：Pages 项目 → Settings → Functions → D1 database bindings → Variable name = `DB`，D1 database = `equipment-booking`
5. **触发部署**：Deployments → Retry deployment（或推一次 main）。1~2 分钟后拿 `*.pages.dev` 域名
6. **回填**：D1 database_id 写进 `wrangler.toml`，域名写进 `docs/任务看板.md`

### 11.8 D1 vs node:sqlite 差异（如实记录）

| 项 | node:sqlite（本地） | D1（线上） |
|---|---|---|
| API 风格 | 同步 | 异步（Promise） |
| 返回值 | `{lastInsertRowid, changes}` | `{meta: {last_row_id, changes}}` |
| 查询结果 | `.all()` 直接返回数组 | `.all()` 返回 `{results, meta}`，需取 `.results` |
| 唯一冲突 | `SQLITE_CONSTRAINT` + `UNIQUE constraint` | 相同（D1 仍 SQLite 方言） |
| 持久性 | 文件本地 | 远程数据库，重启不丢 |

线上 D1 数据持久，不像 Render ephemeral 会重启清库——这是 Cloudflare 路线相对 Render 的额外优势。

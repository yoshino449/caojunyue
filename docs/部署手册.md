# 部署手册：把教务器材预约部署到 Cloudflare（主）+ Render（备选）

> 写给下届同学：照着一步步来，半小时内拿到一个手机可打开的线上地址。AI 生成 + 人工校对版。
> 路线选择：① **Cloudflare Pages + D1（主流程，推荐）**——Free $0/月、不要绑卡、不要手机号、可用 GitHub OAuth、国内可直连（有中文验证码）、数据持久（D1 远程 SQLite，重启不丢）；② **Render（备选）**——Free $0/月、国内可直连，但**首次创建 Web Service 必须绑 Visa/Mastercard 国际卡做身份验证**，无国际卡无法通过；③ Sealos DevBox 已弃（改版后流程不匹配）。
> 为什么换到 Cloudflare：Render Free 要绑国际卡（学生大概率没有），Sealos DevBox 改版后流程不匹配。Cloudflare 实测**完全免费、不要绑卡**，且 D1 数据持久（不像 Render ephemeral 重启清库）。代价：要改架构，后端从 Node http + node:sqlite 换成 Pages Functions（ESM）+ D1 binding，但**本地 `npm start` 路径完全保留**，详见技术方案 §11。

**实测踩过的坑**（2026-10-08 首次部署实录）：

1. **误建 Workers 项目**：Cloudflare 现在把 Pages 和 Workers 合并到同一个 "Workers & Pages" 入口，创建时选错类型会用 `npx wrangler deploy`（Workers 命令）构建，报 `Missing entry-point to Worker script or to assets directory`。认准 **Pages** 类型（域名是 `*.pages.dev`），Build command 留空、Build output directory 填 `frontend`。
2. **D1 API 与 node:sqlite 不同**：取单行 D1 用 `.first()`，不是 node:sqlite 的 `.get()`。误用会抛 Error 1101（Worker threw exception），且 Cloudflare 错误页不显示具体堆栈——用 D1 Console 直接跑 SQL 排查（Workers & Pages → D1 → 数据库 → Console 标签）。
3. **诊断 D1 是否建表成功**：`SELECT name FROM sqlite_master WHERE type='table';` 应列出 `bookings` 和 `visits`；`SELECT * FROM visits;` 应有 `id=1, count=N` 一行。

# 第一部分：Cloudflare 主流程（推荐，不绑卡）

## C0. 这个项目是什么

一个零 npm 依赖的网页：选器材、选日期时段预约，同一器材同一时段互斥。前端单文件 `frontend/index.html`，本地后端 Node 22 内置 `node:sqlite`；**线上用 Cloudflare Pages Functions + D1**（远程 SQLite，平台注入，不算第三方驱动）。前端 fetch 相对路径 `/api/bookings` 等，**Cloudflare 与本地路径完全一致**，前端代码一行不改。

## C1. 前置准备

需要两样东西：**GitHub 账号** + **代码在 GitHub**（Cloudflare 只接 GitHub/GitLab，不接 Gitee）。

### C1.1 注册 GitHub 账号（已有跳过）

浏览器打开 https://github.com/signup ，邮箱注册（国内邮箱可注册，无需梯子，加载稍慢但能进）。

### C1.2 把 Gitee 仓库镜像到 GitHub

Cloudflare 只接 GitHub/GitLab，不接 Gitee。把仓库搬一份到 GitHub（不影响 Gitee，两边都能继续推）：

**方法 1（最省事，不敲命令）— GitHub Import：**

1. 登录 GitHub，访问 https://github.com/new/import
2. **Your old repository's clone URL** 填 Gitee 地址：`https://gitee.com/cao-junyue/caojunyue.git`
3. **Repository name** 填 `caojunyue`
4. 点 **Begin import**，等几秒到几十秒，GitHub 给你一个 `https://github.com/你的用户名/caojunyue`，代码全在。

**方法 2（双 remote，以后两边都推）：**

## C2. 注册 Cloudflare 账号

1. 浏览器打开 https://dash.cloudflare.com/sign-up （国内可直连）。
2. 注册方式四选一：
   - **Continue with GitHub**（推荐，下一步要连 GitHub，最省事）；
   - Continue with Google；
   - Continue with Apple；
   - 邮箱 + 密码。
3. 提交后会出现中文 CAPTCHA「请验证您是真人」，勾选通过。
4. 注册后进 https://dash.cloudflare.com 控制台首页。

> **完全不要绑卡、不要手机号验证、不要实名认证**——这是相对 Render 的关键优势。Cloudflare Free 计划真正免费、可用 $0 跑满。

## C3. 先创建 D1 数据库（必须先于 Pages）

D1 是 Cloudflare 的远程 SQLite，免费档 5GB 存储、500 万行/天读取、10 万行/天写入，对本项目绰绰有余。先建库是为了部署 Pages 时能立即绑定。

1. 控制台首页左侧导航找 **Storage & Databases** 分类，展开后点 **D1**（首次进入会显示介绍页，点 **Create database** 跳过）。
2. 点 **Create database** 按钮：
   - **Database name** 填 `equipment-booking`（自取，会拼进 binding）
   - **Region**（可选）：选离你最近的（国内 Default 即可，Cloudflare 是边缘网络，不强依赖单一区域）
3. 点 **Create**，几秒后跳到数据库详情页。

### C3.1 导入 schema（建表 + 示例数据）

1. 数据库详情页顶部切到 **Console** 标签（直接执行 SQL）。
2. 打开本地仓库 `db/schema.sql`，**全选复制**，粘进 Console 输入框，点 **Execute**。
3. 再打开 `db/seed.sql`，**全选复制**，粘进 Console 输入框，点 **Execute**。
4. 切到 **Tables** 标签，应能看到两张表：`bookings`（2 条 seed 数据）、`visits`（1 条 count=0）。

> D1 完全兼容 SQLite 方言，`CREATE UNIQUE INDEX`、`INSERT OR IGNORE`、`AUTOINCREMENT`、`CHECK` 约束都支持，**schema.sql 一字不改**。

### C3.2 复制 database_id（部署回填要用）

数据库详情页 → 右上角 **API** 或 **Get API link** 按钮，能看到一串 UUID 形如 `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`——这就是 `database_id`，复制保存好，等部署完成后回填到仓库根 `wrangler.toml`。

## C4. 创建 Pages 项目（连接 GitHub 自动构建）

1. 控制台左侧导航点 **Workers & Pages**（首次进入会显示介绍页，点 **Get started** 跳过）。
2. 点右上角 **Create application** → 选 **Pages** 标签 → 选 **Connect to Git**。
3. 第一次会让你授权 Cloudflare 访问 GitHub 账号：
   - 推荐选 **「仅授权特定仓库」**（更安全），勾选你的 `caojunyue` 仓库；
   - 授权后回到 Cloudflare，仓库列表里出现 `你的用户名/caojunyue`，点 **Begin setup**。
4. 进入项目设置表单，按下表填（项目实际值）：

   | 字段 | 值 / 说明 |
   |---|---|
   | **Project name** | `caojunyue`（自取，会拼进域名 `caojunyue.pages.dev`） |
   | **Production branch** | `main` |
   | **Framework preset** | 选 **None**（前端无构建，单文件直接托管） |
   | **Build command** | 留空（前端无构建链） |
   | **Build output directory** | `frontend`（仓库根的 frontend/ 目录，里面是 index.html） |
   | **Root directory** | 留空（仓库根就是项目根） |
   | **Environment variables** | 留空（无需额外环境变量，D1 binding 单独配置，见 C5） |

5. 点 **Save and Deploy**，1~2 分钟后部署完成。
6. 部署成功后页面顶部出现公网地址：`https://caojunyue.pages.dev`（按你的项目名拼）——但**此时 API 还不能用**，因为没绑定 D1 binding，下一步。

## C5. 配置 D1 binding（让 Functions 能访问数据库）

1. 进入 Pages 项目详情页 → 顶部切到 **Settings** 标签。
2. 左侧子菜单找 **Functions**（或 Functions & Intercepts），找 **D1 database bindings** 区块。
3. 点 **Add binding**：

   | 字段 | 值 |
   |---|---|
   | **Variable name** | `DB`（**必须大写 DB**，与 `functions/_lib/queries.js` 调用的 `env.DB` 一致） |
   | **D1 database** | 选 `equipment-booking`（C3 创建的） |
   | **Environment** | 选 **Production**（也可同时加 Preview，本地预览用） |

4. 点 **Save**。
5. **触发新一次部署**让 binding 生效：顶部切到 **Deployments** 标签 → 找最近一次部署 → 点 **...** → **Retry deployment**（或本地 `git push github main` 推一次空 commit 触发自动构建）。

## C6. 验收

打开你的 `*.pages.dev` 域名自检 + 教师手机验收：

| 检查项 | 通过标准 |
|---|---|
| 首页 `https://你的域名.pages.dev/` | 三张器材卡片（投影仪 / 单反相机 / 便携音响）+ 页脚「本页已被访问 N 次」+ 右上角「📊 统计」按钮 |
| 健康检查 `https://你的域名.pages.dev/ping` | 返回 `ok`（裸字符串） |
| 预约列表 `https://你的域名.pages.dev/api/bookings` | 返回 JSON 数组（含 2 条 seed 示例数据） |
| 访问统计 `https://你的域名.pages.dev/api/visits` | 返回 `{"count":N}`，刷新首页 N 递增 |
| 预约统计 `https://你的域名.pages.dev/api/stats` | 返回 `perEquip` 与 `perSlot` 两条聚合数组 |
| 点「📊 统计」按钮 | 弹出柱状图（各器材预约量）+ 饼图（各时段热度） |
| 教师手机 4G 打开 | 首页可正常显示与交互（Pages 冷启动 < 5 秒，比 Render 快） |

## C7. 坑在哪（提前避雷）

1. **必须先建 D1 再建 Pages**：顺序反了 Pages 第一次部署会因找不到 binding 而失败。即便反了也别慌，按 C5 配 binding 后 Retry deployment 即可。
2. **binding 变量名必须大写 `DB`**：写成 `db` 或 `Db` 会导致 `functions/_lib/queries.js` 里 `env.DB` 取不到，所有 API 返回 500。
3. **Build output directory 必须填 `frontend`**：填 `/` 或留空会找不到 index.html，Pages 报 404。
4. **改了 functions/ 后必须重新部署**：本地 `git push github main` 推一次 → Cloudflare 检测到 push 自动重新构建（开了 Auto-Deploy 的话，1~2 分钟后线上是新版）。**域名不变，D1 数据持久不丢**。
5. **D1 Console 粘贴 SQL 时确认带分号**：`db/schema.sql` 多条语句用分号分隔，一次性粘贴执行没问题；如果只复制了一半（没分号），D1 会等下一段，看起来像卡住。
6. **国内访问 pages.dev 偶尔被劫持**：少数情况下 `*.pages.dev` 在国内会被运营商劫持到广告页。**对策**：刷新一次或换 4G 流量；不影响教师验收。
7. **visits 表第一次部署时已 seed 了 count=0**：所以第一次打开首页会显示「本页已被访问 1 次」（自增后），正常。
8. **修改数据库结构后**：本地改 `db/schema.sql` 后，要手动去 D1 Console 重新粘贴执行（D1 不会读仓库文件）。**但本项目 schema 已稳定，T2 阶段不应再改表结构**。

## C8. 日常更新流程

本地改完代码 → `git push origin main` 推 Gitee → `git push github main` 同步 GitHub → Cloudflare 检测到 main 分支 push → 自动触发重新构建部署（1~2 分钟后线上是新版）。**域名不变，D1 数据持久**。

也可在 Cloudflare 控制台手动触发：Pages 项目 → Deployments → 找最近一次 → **...** → **Retry deployment**。

## C9. 回填仓库（部署后必做）

1. 把 C3.2 复制的 D1 `database_id` 填进仓库根 `wrangler.toml` 的 `database_id = "<部署后回填>"` 占位符。
2. 把 `*.pages.dev` 域名写进 `docs/任务看板.md` T2 行。
3. `git commit -m "docs(T2): 回填 Cloudflare 部署域名与 D1 database_id"` → `git push origin main` + `git push github main`。

## 3. 创建 Web Service

## 5. 坑在哪（提前避雷）

1. **必须带 `--experimental-sqlite`**：Start Command 写成 `node backend/server.js` 会在第一次预约时抛 `Cannot find module 'node:sqlite'`。Render 控制台 → 服务 → Settings → Start Command 改回 `node --experimental-sqlite backend/server.js` 后 Manual Deploy 即可。
2. **Free 层 15 分钟 spin down**：Free 计划的 web service **15 分钟无请求会休眠**，下次访问需 30~60 秒冷启动唤醒，期间浏览器显示 Render 加载页。这是免费层已知限制，不是 bug。**对策**：① 教师验收前自己先访问一次预热；或 ② 升级到 Starter（$7/月）取消休眠。
3. **重启清库（ephemeral 文件系统）**：每次重新部署 / 重启 / spin down 唤醒，`data/equipment.db` 文件会丢失。但 `server.js` 启动调 `ensureDb()` 幂等建表 + seed 自愈，所以页面永远不会空——预约数据回 2 条示例、**访问计数归零**。**已知限制，不修**（持久化需付费挂持久卷，超出 T2 范围）。
4. **Node 版本默认 24**：Render Node runtime 默认 24.21.0，满足 `node:sqlite` 所需 ≥22。如需固定版本，在服务 Environment 里加环境变量 `NODE_VERSION=22`（或仓库根加 `.node-version` 文件，内容就一行 `22`）。
5. **PORT 走环境变量**：Render 默认注入 `PORT=10000`，`server.js` 已 `const PORT = process.env.PORT || 3000` 适配。**不要硬编码 3000**，否则 Render 检测不到端口绑定、部署失败。
6. **监听 0.0.0.0**：Node 原生 `http.createServer().listen(PORT)` 默认监听所有网卡，满足 Render 公网转发要求。**不要手改成 `127.0.0.1`**，否则外网访问不到。
7. **Build Command 留空还是 `npm install`**：本项目 `package.json` 无 `dependencies`，Render 会跳过 install。留空最干净；若 Render 强制非空，填 `npm install` 也无副作用。
8. **GitHub 仓库必须最新**：本地改完代码 → `git push origin main` 推 Gitee → `git push github main` 同步 GitHub → Render 检测到 push 自动重新部署（开了 Auto-Deploy 的话）。**两边都要推**，别只推 Gitee。
9. **首次部署可能失败一次**：如果第一次部署卡在 Building 阶段几分钟无进展，多半是 Render 在拉镜像或冷启动构建节点，再等一两分钟；超 5 分钟看 Logs（服务详情页 → Logs 标签），常见原因就是 Start Command 漏了 `--experimental-sqlite`。

## 6. 日常更新流程

本地改完代码 → `git push origin main` 推 Gitee → `git push github main` 同步 GitHub → Render 检测到 main 分支 push → 自动触发重新构建部署（开了 Auto-Deploy 的话，1~3 分钟后线上是新版）。**域名不变，容器重建后数据清回 seed**。

也可在 Render 控制台手动触发：服务详情页 → 右上角 **Manual Deploy** → **Deploy latest commit**。

## 附录 A：用 `render.yaml` 一键配置（Blueprint）

仓库根已有 [`render.yaml`](../render.yaml)，是 Render 的声明式配置（Infrastructure-as-Code）。如果你不想手填表单，可以这样：

1. 控制台首页点 **New** → **Blueprint**（不是 Web Service）。
2. 选 Git Provider → 连接 GitHub → 选 `caojunyue` 仓库。
3. Render 自动检测到仓库根的 `render.yaml`，按其内容创建服务（type/name/runtime/branch/plan/startCommand/healthCheckPath/autoDeploy 全部声明在内），无需手填。
4. 点 **Apply**，等部署完成拿域名。

`render.yaml` 内容（已就位，无需改）：

```yaml
services:
  - type: web
    name: caojunyue
    runtime: node
    branch: main
    plan: free
    buildCommand: ""        # 零 npm 依赖，无需 install
    startCommand: "node --experimental-sqlite backend/server.js"
    healthCheckPath: /ping
    autoDeploy: true
```

> Blueprint 路径与手动路径效果一致，区别只是省去手填表单的步骤。**第一次部署推荐手动路径**，能看到每一步实际值，便于排错；稳定后想重新部署可改用 Blueprint。

## 附录 B：用 Dockerfile 部署到 Render（绕过 Node runtime）

仓库根已有 [`Dockerfile`](../Dockerfile)（`FROM node:22-slim` + `--experimental-sqlite` + EXPOSE 3000）。如果担心 Render Node runtime 版本兼容性，可改用 Docker runtime：

1. 控制台 **New** → **Web Service** → 选 GitHub 仓库。
2. **Runtime** 不选 Node，选 **Docker**。
3. Render 自动读取仓库根 `Dockerfile` 构建。
4. 其余字段（Name / Region / Branch / Free 计划）同主流程。
5. **Health Check Path** 仍填 `/ping`。

> Docker 路径与 Node runtime 路径效果一致，构建稍慢（多一层 Docker build）。**除非遇到 Node runtime 报怪错，否则不推荐**，主流程已验证可用。
